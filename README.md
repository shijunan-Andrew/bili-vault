# 哔哩藏库 Bili Vault

> 把 B 站收藏夹备份本地，启用后，收藏成功自动保存视频资料到本地，支持已有收藏夹视频的本地归档与失效视频恢复，支持本地收藏夹浏览、搜索与筛选。

这是一个 Chrome Manifest V3 扩展。它监听 B 站视频页的收藏夹弹窗；用户确认后，等弹窗成功关闭，再将视频信息和封面写入你选择的本地目录。扩展不拦截或改写 B 站页面的网络请求。

## 使用说明

> **这份文档怎么读**：先用「安装」装好、用「从 B 站收藏夹导入」把收藏夹搬到本地，之后日常只看「本地收藏库」和「把本地视频放进收藏夹」；出问题看「错误报告」。插件界面里另有一份更简略的「使用须知」（插件弹窗右上角的「使用说明」链接、设置页里的「打开使用说明」，都指向 `guide.html`），**风控提醒以那一份为准**。

### 安装

1. 在 Chrome 打开 `chrome://extensions`。
2. 打开右上角的“开发者模式”。
3. 点击“加载已解压的扩展程序”，选择本项目文件夹。
4. 点击工具栏中的“哔哩藏库”，选择本地备份文件夹。
5. 打开 B 站视频页并收藏视频。保存结果会在视频页右下角弹出。

### 保存结构

```text
本地备份文件夹/
├── 收藏夹名称/
│   └── 2026年10月08日21时05分30秒/
│       ├── 封面.webp          # 4.9 之前建的记录是 封面.png，读取时两个名字都认
│       └── 视频信息.txt
├── 000视频下载/               # 视频下载目录（默认位置）
├── 001错误报告/               # 导入或下载失败时写入的错误报告
├── 002同步报告/               # 「与 B 站对比」的结果，只有对比过才会有
└── 003database/               # 本地数据库（database.json），数据统计页的数据源
```

除了 `视频信息.txt` 和封面，插件不会往你的收藏夹目录里写别的东西；上面四个编号目录都是它自己创建和维护的，可以随时删（删了会在下次用到时重建）。

同一收藏夹在同一秒内发生多次保存时，后续记录目录会自动添加 `_2`、`_3` 等后缀，避免覆盖已有文件。

### 从 B 站收藏夹导入

1. 在 Chrome 中打开已登录账号的 B 站个人空间收藏夹页面（`space.bilibili.com/.../favlist`）。
2. 点击插件图标，选择“导入或更新”，勾选要导入的收藏夹。拿不准要不要导时，先点“先看差异”：它只对比收藏夹列表、不抓每条视频的详情（1000 条约 1 分钟），不会改动任何本地文件。确认后点“开始导入”。
3. 视频会按“收藏夹名称/收藏时间”归档到已选择的本地备份文件夹。若目标本地收藏夹已有相同 BV/av 号，会提示“已存在相同视频”并跳过重复项，只导入缺少的条目。
4. 对失效视频，插件会尝试从 APP 收藏夹接口、稍后再看、观看历史和视频资料接口找回标题、封面、UP 主、简介、时长、分区、发布时间和标签。APP 收藏数据会跨页扫描并重试，某页失败时仍保留已读取的恢复结果。未找回的字段记为“未知”；封面无法找回时会保存占位封面，确保本地收藏库仍能显示这条记录。
5. 单条视频或收藏夹导入失败时，其余条目仍会继续处理；错误报告会写入本地备份文件夹下的“001错误报告”文件夹。请避免一次导入过多内容，以免频繁 API 请求触发 B 站风控。

失效视频只有在 B 站仍保留于 APP 收藏、历史记录、稍后再看或视频资料等来源时才能找回；如果这些来源都没有留存，插件会按“未知”保存缺失字段。

导入仅读取 B 站收藏数据，不会修改线上收藏夹。

**请求速度是全插件唯一会影响账号安全的一档设置。** 插件弹窗里的“请求速度”决定向 B 站发请求的间隔，默认是**“较低”**（间隔 1200ms，每 8 条还会停顿 6 秒）—— 它是四个档位里唯一带分批停顿的，导入大收藏夹请一直用它。“标准 / 较高 / 高”分别是 800 / 400 / 200ms，选“较高”及以上时插件会先弹一次风险提示。

**但把速度调快并不会让导入变快。** 抓取每条视频的详情有自己独立的间隔下限（800ms），所以“较高”“高”只让“读收藏夹清单”和“先看差异”快一点，却实实在在地增加风控风险。**没有必要为了快而挂在快档位上。**

导入过程中可以随时“暂停导入”或“取消导入”。取消会删掉本次新建的视频目录、并还原本次更新过的记录；**导入前就在本地收藏夹里的内容不会被删除**。

### 与 B 站对比

收藏夹是会变的：线上多了新视频、少了旧视频，有的视频失效了，有的又恢复了。**“与 B 站对比”只读 B 站的收藏夹列表，不抓每条视频的详情**（所以 1000 条约 1 分钟，比导入快得多），对比过程不会改动任何本地文件。

两个入口：插件弹窗导入面板里的“先看差异”，和本地收藏库右上角的“与 B 站对比”。

结果会按收藏夹列出四类差异：线上有而本地没有的、线上已移除的、新失效的、以及本地标着失效但线上又恢复正常的。完整列表会写进本地备份文件夹的 `002同步报告` 文件夹，可以直接用文本编辑器打开。**对比不会自动补下视频**——它只告诉你差在哪，要不要导入由你决定。

### 错误报告

保存失败时，扩展会尝试在所选本地备份文件夹的 `001错误报告` 子目录中写入报告。若目录不可访问，错误报告会留在扩展弹窗中，可通过“下载错误报告”保存到本地。

### 本地收藏库

点击扩展弹窗里的“打开本地收藏库”，首次选择本地备份文件夹后，页面会记住该目录；之后重新打开时会自动读取，若 Chrome 要求再次授权，可继续使用上次目录，无需重新选择。页面只解析符合“本地备份文件夹 / 收藏夹 / 时间戳目录 / 视频信息.txt + 封面.webp”结构的视频记录（4.9 之前建的记录用 `封面.png`，两种都能读）。目录内容仅由浏览器在本机读取。

**找视频。** 左侧是收藏夹列表，**可拖动上下调整顺序**，顺序会记住。顶部一排是：筛选菜单（全部 / 已失效 / 已下载）、搜索框、排序、本地收藏夹占用体积、“与 B 站对比”、“刷新”（重新扫描当前目录）、“选择本地备份文件夹”，以及网格与竖列两种显示的一键切换；列表底部可选每页 25 / 50 / 100 个。

点击视频卡片打开详情。**封面和标题都能点开 B 站那条原视频**，标签点一下跳到 B 站的标签搜索页，BV 号与视频链接可一键复制。**失效视频在 B 站已经没有能看的页面，所以它们的封面与标题改去 Bing 搜标题**（和详情里那条“全网搜索该视频”同一个出口），标题显示为红色、封面加灰色蒙层。

左侧栏底部还有几项：新建收藏夹、一键三连与 Github 仓库地址，以及**“导出配置”/“导入配置”**。配置里只有界面偏好——主题、语言、每页数量、网格还是竖列、收藏夹顺序，以及当前的筛选与搜索词；**它不含任何目录句柄、B 站数据，也不含自定义背景图**——图片只存在你本机，导出配置带不走它。换台电脑时可以用它把界面调回原样。

**改归档。** 网页可新建或删除本地收藏夹，也可选择一个或多个目标收藏夹添加视频。输入 B 站视频网址、BV 号或 av 号后，扩展会向 B 站查询视频资料，再分别写入未包含该 BV/av 号的收藏夹；遇到重复项会提示“已存在相同视频”并跳过该收藏夹。

在视频详情或批量管理中点击“移动或复制”，可以同时选择多个目标收藏夹，**列表里会标出这条视频当前躺在哪些收藏夹（“已收录”）**。勾选视频原所在的收藏夹时会保留原文件并复制到其他已选收藏夹；不勾选时会把视频放入所选收藏夹并删除原位置。目标收藏夹已有相同 BV/av 号时会提示并跳过重复项，其余目标继续处理。删除视频或整个收藏夹前会请求本地目录写入权限，并显示确认提示。

点击“批量管理”后，视频卡片会显示勾选框，可全选当前筛选结果，再把多个视频移动或复制到一个或多个收藏夹，或批量删除；按住 `Shift` 可连选，`Ctrl` / `⌘` + `A` 全选。批量删除前会显示确认提示；失败的视频会保留选中，便于重试。

**外观与语言。** 收藏库右下角挂着**两个圆球**：上面是**回到顶部**（往下滚过一屏才淡出来），下面是**齿轮**。点齿轮打开独立的**设置页**（`settings.html`）：外观、语言，以及「打开安装教程」「打开使用说明」两个入口。**外观**有四项：跟随系统 / 白天 / 夜晚 / 自定义；选「自定义」后可以挑一张本地图片当整页背景，再调**背景遮罩透明度**与**背景模糊强度**，还能开**毛玻璃**（侧栏、卡片、对话框变成半透明的磨砂质感，另有一个 1–20px 的玻璃强度）。**语言**是简体中文 / 繁體中文 / English。改完**立即生效、人留在设置页**；选择会记住，下次打开直接生效；**换背景图时已经开着的收藏库也会立刻跟着换，不用刷新**。插件弹窗里只能切语言，改的是同一个设置。**界面上的目录名与文件名不随语言变化**——界面上的 `000视频下载` 就是磁盘上的 `000视频下载`，任何语言下都不翻译。

如果浏览器回收了本地目录的写入授权，扩展弹窗会显示“重新授权本地备份文件夹”。授权后，近期失败且已暂存的视频会自动补存；较早版本失败时没有暂存内容，需要在 B 站重新收藏一次。

### 把本地视频放进收藏夹

**1.3.0 起，插件不再提供下载功能。** 出于安全考虑，插件不再请求视频流地址、也不再保存视频本体 —— 它只读取收藏夹和视频资料。你仍然可以用别的方式把视频下载到本机，再把它放进收藏夹里，这样收藏库同样能认出它。

1. 在本地收藏库的视频详情里点击**「将下载到本地的视频放入收藏夹中」**。（批量管理里那个“下载”按钮已经在 1.3.0 一并移除。）
2. 插件会在本地备份文件夹的 `000视频下载/收藏夹名称` 下，按 `标题 - BV号` 建好这条视频的目录，里面只放一个说明文件 `请将视频放到这里.txt`，**没有视频内容**。
3. 把你下载好的视频文件复制或移动进这个目录。

目录内存在视频或音频媒体文件时，收藏库的视频卡片会显示“已下载”。安装下方的 Windows 辅助程序后，详情页的“打开本地视频目录”会直接打开对应的资源管理器文件夹；未安装时会提示安装方式。删除目录中的所有文件后，收藏库会在你切回该页面或重新打开时撤销标记和入口。

目录结构和归档目录一一对应，所以你完全可以手工建目录、手工放文件，效果一样；插件只是替你省掉找路径这一步。

插件弹窗与本地收藏库顶部的“使用须知”都默认收起，点一下展开；里面第一条“请勿滥用、请分批低速使用”是整份文档里最要紧的提醒。

#### Windows 文件资源管理器

Chrome 不允许扩展页面直接启动 Windows 文件资源管理器。若要使用详情页的“打开本地视频目录”，需要一次性安装随插件提供的原生辅助程序：

1. 先在 Chrome 中加载本插件，打开 `chrome://extensions`，复制本插件的扩展程序 ID。
2. 双击 `install-native-folder-opener.bat`，粘贴扩展程序 ID 和视频目录完整路径。默认位置应填写“本地备份文件夹\000视频下载”。
3. 在 `chrome://extensions` 中重新加载本插件，然后完全退出 Chrome（关闭所有窗口，必要时在任务管理器结束 chrome.exe）并重新打开。
4. 打开本地收藏库，点击“打开本地视频目录”。

安装脚本会用 Windows 自带的 C# 编译器把 `native\folder-opener-launcher.cs` 编译成宿主启动器 `folder-opener-launcher.exe`，放进 `%LOCALAPPDATA%\BcaFolderOpener`，并写入 Chrome 原生消息清单和当前用户注册表。**扩展程序 ID 是由插件所在目录的绝对路径决定的**：换了插件目录（例如从 `bili-vault-beta4.9` 换到 `bili-vault`）ID 就会变，此时必须用新 ID 重新运行一次安装脚本。**所以尽量不要重命名这个文件夹。**

安装后可以先做一次不依赖 Chrome 的自检（不会打开资源管理器）：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\test-native-folder-opener.ps1 -CollectionName "收藏夹名称" -DirectoryName "视频目录名称"
```

如果本地目录打开助手不可用，“打开本地视频目录”会在视频详情里保留完整错误原因，并提供“复制视频目录路径”：助手可用时复制完整绝对路径，不可用时复制“收藏夹\视频目录”相对路径，可手动粘贴到资源管理器。

辅助程序只会打开配置的视频目录中的“收藏夹/视频”子文件夹。它以当前 Windows 用户权限运行，不需要管理员权限；卸载时运行 `uninstall-native-folder-opener.ps1`。如果更换扩展程序 ID 或视频目录，需要重新运行安装脚本。安装前 Chrome 会提示扩展新增了“与协作的原生应用通信”权限。

### 开关与本地整理

扩展弹窗中的开关控制自动归档；开启时工具栏图标为蓝色，关闭时为灰色。关闭自动归档不会影响本地收藏库。打开视频详情后，可将归档目录移动或复制到本地收藏夹，也可删除这条视频的本地归档文件；这些整理操作不会修改 B 站账户中的收藏。

**插件里只有一个“本地备份文件夹”的设置。** 弹窗里的“选择本地备份文件夹”和收藏库右上角的同名按钮，指向的是同一个目录 —— 在哪边改都生效，另一边会跟着变。

## V1.7.7：把「开着收藏库就一直在转」的那个环路关掉

你让我做的第二份性能审计（后台 / 空闲期真正会发作的重活）报了两条 P0 和五条 P1，这一版全部修掉。最要命的一条是**一个不会自己停的循环**：

- **收藏库不再自己喂自己**。收藏库扫完一遍会把统计快照写进 `bcaStats`，而它自己正好订阅着这个键 —— 于是「写 → 收到自己的变更 → 900ms 后重扫 → 再写」，不用导入、不用操作，**开着收藏库页就每秒转一轮**（每秒写 227KB 数据库 + 一次 storage 写，扩展的后台进程因此永远不被回收）。现在写之前先比实质内容（时间戳不算），自己的回声也不再触发重扫。这大概就是你之前反复看到「正在读取 N/M…」和「一直进不去」的根源。
- **切回标签页不再整树重扫下载目录**。那次扫描是上万次文件系统调用（几千个目录），而「下载真的写完了」本来就有专门信号。现在只有那个信号、或距上次扫描超过 60 秒才会扫；窗口获焦那条重复的监听直接删了。
- **写库不再每次都整份复制一份 `database.bak.json`**（摸一次宠物就白写 227KB）。轮转改成 10 分钟内至多一次。
- **导入进度不再每 500ms 落一次盘**（那是后台进程无法回收的另一个来源）。
- **统计页不再因为「只有时间戳变了」就整页重画图表**（加了实质比较 + 300ms 防抖）。
- **B 站视频页每次点击的判定变便宜**（不再对整条路径上的每个叶子节点做样式/布局计算）。
- **封面缓存上限从 4000 收到 600**（页面同时只显示 25 张卡）。

测试：196 项静态检查 + 59 项归档纯函数 + 58 项数据库纯函数全绿；两条 P0 的验证台 9/9。

## V1.7.6：饼图分块改回「看排名」

按你的口径把饼图的切法换成**数量排名**：前 5 名的收藏夹各自一块、显示完整名字，第 6 名及以后并成一块「其它收藏夹」（年度构成饼图同理，第 6 个年份起并进「其它年份」）。1.6.5 那套「不足 3% 并块」的规则去掉了。

- 收藏夹 ≤5 个：每一个都有自己的名字。
- 收藏夹正好 6 个：前 5 名按名字显示，第 6 名进「其它收藏夹」。

## V1.5.4：宠物只做三件事 —— 眨眼、坐下、睡觉

走路那一段**删掉了**。原因见说明书里的技术记录：那张精灵表的「走路」两行其实是同一个站立姿势复制了六份，逐像素差异图显示变化全落在轮廓的抗锯齿上，没有一块肢体在动 —— 没有腿可动，就不硬做走路。

现在是一个固定的循环：

- **待机** 4–8 秒，期间眨 1–3 次眼（每次 140 毫秒，只闭一次眼）；
- **坐下** 360 毫秒（身体下压 2 像素并轻微压扁）；
- **保持坐姿** 4–8 秒；
- **睡觉** 10–30 秒（每轮随机，四次实测 11.0 / 12.2 / 15.7 / 26.1 秒）；
- **站起来**：把坐下那段过渡**反向播放**（360 毫秒），然后回到待机。

**点一下正在睡觉的猫会把它唤醒**，它站起来、眨眨眼，并且 8–15 秒内不会立刻又睡。

- **气泡以前不自动消失** —— 老代码里根本没有任何计时器，唯一能收起它的路径是「点满五句」，而页面点击又被宠物自己的 stopPropagation 挡住了。现在**出现 5 秒后自动收起**，每次点击重新计时，一轮的话说完后下一击收起，按住拖动期间不收。
- **拖不到上方** —— 纵向钳制只算了「向下的空间」（44 像素），算出来的向上空间是个从未被使用的死变量，所以猫只能在最下面那条窄带里挪。现在上下合计 795 像素，能放到视口里任何高度，位置照旧记住。

**升级注意**：纵向正负号的含义变了（现在「正 = 往上」）。如果你之前把猫拖到过最下面，升级后它可能出现在偏上的位置 —— 右键菜单里的「重置位置」点一下就回到底部停靠位，默认位置不受影响。

## V1.5.2：猫变清楚了，而且能拖、能调大小、会自己走动

**先说糊的原因**：不是素材的问题，是我上一版的两个技术选择错了。一是把 222 像素的源图缩到 48 像素显示，却还开着 `image-rendering: pixelated` —— 那个属性只适合「整数倍放大」，用来缩小等于随机丢掉源像素，猫嘴（一两个像素宽）第一个消失。二是为了压体积把图降到了 64 色，「嘴」和「描边」这些靠少数深色像素撑着的细线就被量化糊在一起了。

**改法**：把「缩小」和「放大」分开 —— 构建时就把每帧正确重采样成 48×48 的**逻辑分辨率**并**保留完整 RGBA（零量化）**，运行时只做**整数倍放大**（96 / 144 / 192 / 240 就是 48 的 2/3/4/5 倍）。文件反而从 169 KB 降到 **97 KB**，猫嘴的每一笔都数得出来。

**新能力**：

- **大小四档**：96 / 144 / 192 / 240 像素，右键宠物或在设置页「宠物挂件」里都能改，记忆住。
- **可以拖**：按住猫拖到任意位置，松手记住；拖动和点击分得开（位移超过几个像素才算拖，不会误弹气泡）。位置按视口比例记，换分辨率不会跑到屏幕外。
- **右键菜单**：大小四档 + 暂停走动 / 继续走动 + 重置位置 + 隐藏宠物（自绘菜单，不申请任何新权限）。
- **待机时会自己动**：在「眨眼 / 向右走 / 向左走 / 坐下 / 睡觉」之间随机切换，**眨眼最频繁**（约六成），而且眨眼改成「睁着眼，隔几秒眨一下」的瞬时动作，不是原来那种慢悠悠的循环。
- **走路是真的走**：猫会沿屏幕横向移动，走到边缘停下或换向，绝不走出屏幕。
- **点击反馈**：气泡渐入，猫有按压回弹的弹性。

## V1.4.7：导入时关掉收藏夹页面，弹窗也会如实告诉你结果

**没变的部分**：重新打开弹窗时依旧会补显示上一次的结果。

## V1.4.3：自己审的第二批——收藏库与导入之间不再互相装看不见

上一版（V1.4.2）修的是「会丢东西 / 会认错」的那一类，这一版修的是「看着没事、用起来别扭」的那一类：官方叫 P2，一共十几处。都不影响你已经归档的内容，但每一条你都有可能撞上。

**收藏夹不许占用插件自己的目录名。** `001错误报告`、`002同步报告`、`000视频下载` 这些名字归插件用。以前只有「手动添加」和「导入」两条路会挡，**自动归档那条漏了**：如果你在 B 站真有一个叫「001错误报告」的收藏夹，收藏进去的视频会被写进报告目录里。现在三条路共用同一份名单，撞上就直接不收、并说明原因。

**不会再有假的「导入中」。** 浏览器重启后 `chrome.storage.session` 会被清空，只剩一份「正在导入」的残影。以前要等 90 秒才自动复位 —— 这 90 秒里弹窗显示正在导入、暂停/取消按钮都在，点了却只回一句「当前没有正在进行的导入」。现在判据换成「会话里还有没有正在进行的记录」，没有就立刻复位。

**两句会骗人的提示改了。** ①「更新视频状态」在本地队列被占用时会说「本次状态更新已取消」，但那条任务其实还排在队列里、稍后照样会写回文件 —— 现在说的是「这次不再等它了，任务仍在队列里」。②第一次用「与 B 站对比」而插件还没记住你的 UID 时，原来提示「请先打开一次自己的 B 站收藏夹页面」，但插件没有 `tabs` 权限、那条查询注定找不到页面，照做也没用 —— 现在提示的是真能解决它的动作：先在 B 站收藏夹页面用插件做一次导入。

**封面下载收进限速里，还加了域名白名单。** 封面是唯一一条「不限速、没有超时、同时下 4 张」的出网路径，地址还直接采信页面给的 `og:image`。现在它和 B 站接口共用同一个限速器、20 秒没响应就放弃，并且只允许 `*.hdslb.com` 与 `*.bilibili.com` 两个域名的封面 —— **不在白名单里的地址直接跳过，绝不向任意域名发请求**。另外，详情代取是「页面找不到就回后台直连」，但如果那个收藏夹标签页被关掉或刷新，后台这一侧以前会一直等下去 —— 整轮导入就卡住了，连取消都没用。现在后台自己也有超时，会明确报错并继续。

**错误报告和同步报告不再无限堆积。** 每次失败都会在 `001错误报告` 写一份，以前只增不减、也没有清理入口。现在每个目录保留最新 50 份，旧的自动删掉。

**删下载目录前先确认那是插件写的。** 删掉某个收藏夹在 `000视频下载` 下的下载目录时，先看一眼里面：每一项都得是 `视频名 - BV号` 这种插件自己写出来的子目录，认不出来就整个不删，并在结果里如实报「1 个下载目录未能删除」。**宁可留给你自己删，也不能误删别人的东西** —— 这里的删除不进系统回收站。

**收藏库会告诉你「导入正在进行」。** 导入期间在收藏库里移动、删除、标记「已下载」，两边是互相看不见的：移动进本收藏夹的视频会被本轮判成缺失。现在收藏库顶部会出现一条提示，写清「现在做这些操作可能和导入互相影响，建议等它结束」。**只是提示，不禁用按钮** —— 你可能就是想边导边整理。

**「与 B 站对比」不能同时开两个了。** 以前连点两次会真的发两份请求，谁先谁后不确定，两个结果还会互相清屏，最后画面上是慢的那一份。现在点下去就进入对比中、第二次点不动。

**风险档确认不会再卡死。** 对比时弹出「差异较大，确定要继续吗」的那一步，如果你第二次触发它，第一次等待确认的流程会永远等不到答复（把对话框关掉也回不来）。现在第二次会先把上一次按「取消」结算掉，再开新的。

**换页动画尊重系统的「减少动态效果」。** 换页时强制平滑滚动的那一处没判断这个偏好，已经改成和收藏库其他滚动一致。

**「更新状态」的按钮不再说「取消」。** 请求发出去之后就真的中断不了，按钮现在如实地说「不再等待」，并在结果里说明后台仍会继续写完。

**大收藏库的首屏轻了一点。** 「本地收藏夹占用」原本会为了算体积递归枚举每一个归档目录里的所有文件，筛选时又会为了一个计数再扫一遍全量文件。现在体积统计不再挡着首屏、同一时间只跑一次，筛选计数直接由内存里的结果得出、不再碰文件系统。

测试从上一版的 189 项加到 191 项，全部是静态断言；真机那几项（尤其是「导入期间收藏库的提示条」和「连点对比」）还是要照 `SMOKE_TEST.md` 走一遍。

## V1.4.2：发布前自己审了一遍，把八处边界补上

发布前做了一轮「上线前审查」，按三级严重度各查一遍：会对账号或本地文件造成严重后果的、会让操作直接失败的、会卡住但能恢复的。**没有发现会封号、或者会把已经归档的文件弄丢的现成路径**，但有八处边界值得补，这一版全都补了。

**删除前会告诉你不进回收站。** 删除确认框里多了一行红字：「本地删除不可恢复：不会进系统回收站，删掉就找不回来了。」后端用的是浏览器的文件系统接口，`removeEntry` 不经过回收站，这一点以前只写在文档里。

**删「关联的下载文件」时先确认那个目录确实是本插件写的。** 删除收藏夹时可以顺带删掉 `000视频下载` 下的同名目录，以前是整目录直接递归删。现在它先看一眼：里面的每一项都得是「xxx - BV号」这种本插件生成的视频目录，认不出来就整个跳过，并在结果里报「N 个下载目录未能删除」。宁可留着让你自己删，也不能误删别人的东西。

**导入期间新增的收藏不再无限期等着。** 以前的「保存队列」在导入暂停或进行中会一直挂住，界面只说已排队，你要是关了浏览器那一轮就再也不会执行。现在超过等待上限会明确回一句「本地队列正忙（很可能有一轮导入正在暂停或进行中），这次没有执行。等导入结束或取消后再试一次就好。」，并把这条收藏记下来，下次还能重试。

**「中断的那一轮」不会再认错。** 收尾的几个异步步骤之间如果被浏览器回收（MV3 的 Service Worker 随时可能被停），快照会停在「有一轮正在进行」——于是一次**已经成功**的导入会被下次启动当成「断在中间的那一轮」。现在收尾第一步就把快照标成已结束，识别中断时也只在快照确实还是「进行中」时才认。

**「回滚中断导入」这段代码没有了，那句承诺也改了。** 那个功能一直没有入口（按钮早就删了，只剩没人调用的消息分支），却留着提示语「回滚日志已保存在本次浏览器会话中」——日志只存在本次会话、关掉浏览器就没了，等于给了一个兑现不了的承诺。而且它背后的假设是错的：中断时写进去的记录本身是完整的，重新导入会跳过，本来就不需要回滚。所以这一版把这段代码和那句提示一起删掉，提示改成「它们都是完整记录，重新导入会跳过」。

**几个看不见但会咬人的地方**：三个纯本地读循环补了「保活」，上万条记录时 Service Worker 不会被半路回收；时间目录撞上同名**文件**（不是目录）时不再直接失败，而是换个后缀继续；风控识别补上了 B 站另外两个「请求过于频繁」的返回码（-509 / -799），恢复扫描撞上风控会立刻停下，而不是连打三次。

## V1.2.8：重复导入不再给「没变」的记录刷一遍时间戳

**现象：** 一个 6 个视频的收藏夹（1 条失效 + 5 条正常），导入完再导入一次，报告里写着「更新 3 个」—— 数字每次都一样，明明什么都没改。

**第一层原因：占位值分两种，以前混成了一种。** 标签/简介/发布时间缺失时归档会写成占位值，判断「这条记录资料不全、值得再抓一次」时以前一律当成「上次没取到」。可那 3 条里有一条的 B 站简介本来就是空的，接口回的就是一个 `-`：再抓一百次也还是同一个符号。这一版把符号类占位（`-` `--` `—` `/`）从「值得再抓」里摘出去，只留词类（`未知` `无` `暂无` `N/A` …，这些多半是上一次真没取到）。

**第二层原因（更根本）：文件里那行 `信息保存于` 每次都不同。** 光摘占位还不够 —— 剩下两条的简介是 `未知`，仍会被判成资料不全、仍会去重抓；重抓本身没错，问题在写盘那一步：`视频信息.txt` 里有一行 `信息保存于：<抓取时的当前时间>`，每次刷新都现取一次，于是「新内容」和「旧内容」永远不相等 —— 文件被重写一遍，计数就加一。这一版改成比对**抹掉这一行之后**的正文：除它以外完全一样就不动文件、也不算更新。`信息保存于` 从此只在这条记录的资料真的变了的时候才往前走。

**对用户的影响：** 连着导入两次，第二次这些记录会落在「已存在、跳过」里，不再是「更新 N」。而「资料真变了就跟着变」的能力没丢 —— B 站以后补了简介、播放量涨了、封面补上了，照样重写并计入更新。

测试从 180 项加到 **181 项**。

## V1.2.7：修「导入失败：root is not defined」

**上一版刚把导入放行，下一步就撞上了第二个 bug。** V1.2.6 拆掉那道自锁的闸之后，导入终于能真的往下走了，可是一开始导入就报「导入失败：root is not defined」，一个字都没导进去。这一版把它修掉，导入才算整条路走得通。

**它一直被上一个 bug 挡在门外。** V1.2.0 那一轮改动（就是引入导入自锁的那个提交）为了给「取备份文件夹 → 查授权 → 查有没有勾选」这几步分错误类型，把这段包进了一个 `try` 块；而 `const root = await getRootHandle();` 也跟着落进了这个块的作用域 —— 块一结束，`root` 就没了。导入后面还要拿它建收藏夹目录、交给写单条记录的那一步，这些都写在 `try` 外面，于是走到那儿就抛 `ReferenceError: root is not defined`。

**这类 bug 自动检查一个都拦不住。** 它不是语法问题，`node --check` 过；也不是文本约定，静态断言看不见；只有真跑到那一行才炸。而 V1.2.0 到 V1.2.5 期间那一行根本到不了 —— 上一版那个自锁先把它拒了，所以它一直没露面。

**改法就是一行。** 声明提到函数开头（`let root;`），`try` 里改成只赋值（`root = await getRootHandle();`）。作用域从「那个块」变成「整个函数」，后面所有用它的地方一个字都不用改。

**对用户的影响：** 导入恢复可用。两个 bug 各自的表现不一样 —— 上一版之前是点一次报「已经有一轮导入正在进行」，这一版之前是点一次报 `root is not defined`，都修完才是正常的导入。更新走同一条路，同样受益。

测试从 179 项加到 **180 项**。新加的是一条静态回归，钉住那个作用域：`root` 必须声明在函数里、要在那个 `try` 之前、`try` 里只能赋值不能再声明一次；另挑两处 `try` 之外的用法（建收藏夹目录、写单条记录）当哨兵。

## V1.2.6：修「一导入就说已经有一轮导入正在进行」

**导入和更新从 V1.2.0 起就是坏的，一直到这一版。** 点「开始导入」或「更新」会立刻失败，提示「导入失败：已经有一轮导入正在进行，请先等它结束或取消它」，并且真的什么都没导。同一轮改动里加的「对比差异」不受影响（它不走这条队列），下载也照常 —— 这也正是它容易被漏过的原因：看起来只有导入这一个按钮坏了。

**坏在「自己把自己挡住」。** 那版为了防连点，给导入加了两道闸：消息一进来就在同步代码里记一笔「队列里压着一轮」（`importPending += 1`），任务真正出队时再置位「正在跑」（`claimImportRun`）。问题出在**那笔账什么时候放掉**：原代码要等整轮任务跑完（`.finally`）才放 —— 可任务出队后的第一件事就是 `claimImportRun`，它一看「有排队或有在跑」就退回 null，于是每一轮导入都被自己刚记下的那笔账挡在门口。改法是把放账挪到**出队那一步**（先放掉自己这笔，紧接着 claim；两步之间没有 await，连点照样插不进来）。

**顺手把第二道闸也补上了。** 原来只有 `claimImportRun` 里那一道判断，而它跑在若干 await 之后，连点第二次有机会先排进队列；现在消息处理器在同步代码里就先查一次，被拒的直接回，什么都不入队。两道合起来：连点第二次会被明确拒掉，而且不会把正在跑的第一轮带崩。

**对用户的影响：** 导入和更新恢复可用。以前点一次就报错、什么都没发生；现在照常导入，连点两次会明确告诉你「已经有一轮导入正在进行」。

测试从 178 项加到 **179 项**。新加的这条不是文本断言，而是把消息处理器、`claimImportRun`、`importBiliFavoritesInOrder` 三段控制流从 `background.js` 里抠出来真跑一遍：一次普通导入必须返回成功；第一轮还停在中途时再点一次必须被拒；被拒的那次不能留下没放掉的账。同一套宿主喂给改动前的代码，一次普通导入回的正是那句「已经有一轮导入正在进行」。

## V1.2.2：修「往下滚时，卡片上的标签糊在顶栏上」

- **现象**：往下滚收藏库，视频卡片上那几枚标签（左下角的收藏夹名、右下角的播放量、右上角的「已下载」）会盖在顶栏上，和「本地收藏夹占用」「与 B 站对比」「刷新」糊成一片。顶栏是吸附（sticky）的，本来就该挡住滚上去的内容。
- **根因**：层叠上下文（stacking context）算错了。顶栏 `.topbar` 是 `position: sticky; z-index: 1`，自建了一个 z-index 为 1 的层叠上下文；而卡片徽标挂在 `.card-cover` 上 —— 它只有 `position: relative`、**没有 z-index**，所以**不会**自建层叠上下文，徽标那些 `z-index: 1~3` 于是拿到**根**层叠上下文里去和顶栏比。结果顶栏和「收藏夹名 / 播放量」两枚徽标同为 1：**z-index 相等时由 DOM 顺序决定**，而卡片排在顶栏后面 —— 徽标赢。「已下载」（2）和批量模式的选择框（3）更是直接压过去。
- **修法**：顶栏 `z-index` 从 1 提到 **4** —— 压过全部徽标（最高 3），又仍然低于详情遮罩(5)、右下角悬浮球(6)、开源横幅(7)、确认框(8) 和对话框(10)，所以「打开视频详情时顶栏被半透明遮罩压住」这些原有行为一点没变。
- **顺带**：加了一条静态回归测试，直接读 `library.css` 里的 z-index 比大小，把「顶栏必须**严格大于**每一枚封面徽标、且低于详情遮罩」钉死。改回 1 这条测试就会红（已实测）。

- **教训**：`try` 块里只要有一行在"副作用已经完成"之后执行，那行的任何异常都会被误报成整件事失败。同一段里已经有 `refreshVideoFilterOptions()` / `renderVideos()` 了，多这一行、错这一个名字，代价就是用户以为白干了。

## V1.1.34：修正 V1.1.33 —— 把 `attr` 当位标志是错的

- **V1.1.33 的判据 `(attr & 1) === 1` 写窄了，这版改成 `attr !== 0`。**
- **怎么发现的**：用户提到「失效视频分两种，一种是 UP 自行删除，一种是平台删除」，并指出另一个同类插件 `bili-recovery` 里有对失效原因打标签的逻辑。去读它的源码，找到这张表（`content.js:2074` 的 `ATTR_LABELS`，`summary.js:385` 有同样一份）：

  | `attr` | 含义 |
  |---|---|
  | `0` | 有效 |
  | `1` | 其他 |
  | `2` | **版权原因** |
  | `3` | 违规内容 |
  | `5` | 视频已失效 |
  | `9` | **UP主自行删除** |
  | `11` | 已锁定 |

- **`attr` 是「删除原因」枚举，不是位标志。** 我原来的推理错在哪：抓到的 32 条失效视频取值只有 `1` 和 `9`，**两个都是奇数**，于是误以为最低位是失效位。那纯属巧合 —— 表里 `2`（版权原因）是偶数，按 `& 1` 判会被**当成有效视频**，正是这个改动本来想防的那类静默漏判。
- **正确且更简单的判据是「非 0」**：实测 282 条（哆啦a梦 6 + 沙雕动画 129 + 研 148）里，**250 条有效视频 `attr` 全为 `0`，32 条失效视频 `attr` 全非 `0`**，一一对应，无一例外。
- 测试补上 `attr=2` 和 `attr=11` 两个用例（`& 1` 写法会漏掉它们），并加了一条反向断言禁止退回 `attr & 1`；`attr === 1` 那条反向断言保留 —— **这个判据连着两次写窄了**。
- 教训：**样本里没出现反例，不等于规律成立。** 第一次只抓 7 条失效视频就下结论，第二次抓到 32 条，取值仍然只有 `1` 和 `9` —— 数据量翻了两番，反例照样没出现。真正纠正它的是**别人写的字段取值表**。下次再从数据里看出「规律」，先去查有没有现成的字段定义。

## V1.1.33：失效判据补上 `attr` 字段

> ⚠️ 这一版的判据 `(attr & 1) === 1` 写窄了，已在 V1.1.34 修正为 `attr !== 0`。下面保留当时的原始记录。

- **修的是一个还没发生、但一旦发生就会静默退化的问题。** 判定一条视频是否失效，原来只有两个来源：接口的 `is_invalid` 字段，和标题是否等于「已失效视频」「该视频已失效」。**真机上 `is_invalid` 根本不存在**，所以实际全靠标题字符串匹配。
- **B 站一旦改失效标题的措辞**（比如改成「视频已删除」），标题判据会**静默失效** —— 不报错、不留痕，表现就是"退回旧行为"：失效视频再次被当成普通条目写入，覆盖掉本地记录。这正是之前修了三版的那个坑的形态。
- **这次不再靠读源码推断，而是直接抓真数据。** 用浏览器登录态调收藏夹接口，把「沙雕动画」129 条逐条拉下来对照：

  | `attr` | 条数 | 标题 |
  |---|---|---|
  | `0` | 122 | 全部有效视频 |
  | `9` | 5 | 全是「已失效视频」 |
  | `1` | 1 | 也是「已失效视频」 |

  加上「哆啦a梦」那条 `attr=1`，**7 条失效视频一条不漏地全部 `attr ≠ 0`，122 条有效视频一条不漏地全部 `attr = 0`**。
- **结论：`attr` 是位标志，最低位表示已失效。** 新增 `function importAttrIsInvalid(value) { return (Number(value || 0) & 1) === 1; }`，判据变成三个来源并列：`media.is_invalid === true || importAttrIsInvalid(media.attr) || importIsInvalidTitle(title)`。
- **差点写错的地方**：一开始我打算写成 `media.attr === 1`。真数据显示失效的取值是 **1 和 9 两种** —— 按 `=== 1` 写，那 5 条 `attr=9` 的会**全部漏掉**。所以必须按位与判最低位，测试里也加了一条反向断言禁止退回 `=== 1`。
- 测试用的是**真数据**：`1`/`9` 要判失效，`0`/`2`/`8`/缺失/空串/`"0"` 要判有效（`9 = 8|1`，只有 bit0 算失效位）。

```
① 导入流程先把不可用的标题换成占位符：
     if (!item.isInvalid && !importUsefulTitle(item.title)) item.title = "未知";
② 守卫再去检查 item.title —— 此时它是「未知」
③ 而 importUsefulTitle("未知") 返回 true（它只判"非空且不是已知失效标题"）
④ 守卫放行 → refreshImportedRecord 用 importMetadata → buildInfo 整篇重建文件
⑤ 本地标题被写成「未知」
```

**「未知」是一个占位符，不是数据** —— 但前两版的判据都把它当成了合格内容。

- **新增 `importItemIsTrustworthy()`**：失效、标题空、标题是「未知」，三种都判为不可信，一律不许覆盖本地已有记录。
- **给它补了真跑的单元测试**（这个判据已经骗过我两次，不能再靠读源码确认）：真实标题可信；「未知」「已失效视频」「"  "」「null」都不可信。
- 测试里还加了两条**反向断言**：判据不许退回 `item.isInvalid`，也不许退回 `importUsefulTitle(item.title)`。

> 这个 bug 修了三版才对，根因是我一直在**读源码推断**而不是**执行验证**。所以这次把判据本身变成了可执行的测试对象 —— 前两版如果这么做，第一次就会发现。

## V1.1.21：上一次没修干净 —— 标题仍被覆盖

- **V1.1.20 的拦截条件写窄了，用户复现后发现标题还是变成了「未知」。** 那一版只挡 `item.isInvalid`，但真机上那条视频**根本没被判定成失效**：B 站返回的标题既不是「已失效视频」这类已知占位、也不是可用标题，于是插件按"标题取不到"把它改成了「未知」—— 然后这条「未知」就把本地完好的标题覆盖了。
- **判据放宽成：失效 _或_ 标题不可用，都不许覆盖本地已有记录。** 本地没有的条目不受影响（该存还是要存）；想用降级信息覆盖，只有手动点「更新视频状态」那一条路。
- 报告里的说明也跟着改成通用说法：「有 N 条解析结果不可用（已失效或标题取不到），本地已有备份，按规则保留了原记录」。

> 教训：**"失效"不等于"信息不可用"**。前者是 B 站的一个标记，后者是这个项目真正要防的东西 —— 只要解析结果比本地差，就不该让它落地。

## V1.1.20：失效视频不再覆盖本地记录

**这是一条数据丢失，优先修。**

- **修：重新导入或更新收藏夹时，解析到的失效视频会覆盖本地原来完好的记录。** B 站对失效视频只返回「已失效视频」这类占位信息，拿它去刷新，你本地那条收藏得好好的标题、简介、标签就被「未知」盖掉了 —— 真机上丢过一次：一条视频失效后重新导入，标题变成了「未知」，其它信息也没了。
- **现在的规则**：
  - 解析到失效视频、**本地没有**这条记录 → 正常写入（该存还是要存）
  - 解析到失效视频、**本地已有**这条记录 → **直接丢弃，绝不覆盖**
  - 想用失效信息去覆盖，只有**手动点「更新视频状态」**那一条路
- 报告里会写明这个收藏夹保留了多少条，「已存在跳过」的数字也仍然照常统计。

**顺带两处界面调整**：收藏库的风控提醒改成醒目的红色块，「取消」是蓝色主按钮、「照当前档位继续」是淡色次要按钮（与插件弹窗一致）；插件里「请求速度」下方的说明在「较高」「高」档时也改成红色。

**还有一条行为变化**：请求速度**不再沿用上次的选择** —— 关掉浏览器再打开会回到默认的「较低」。快档是一次性的决定，不该在不经意间被继承下来。

## V1.1.0：同步差异报告

**不用再"跑一次导入"才知道变了什么。** 现在可以在动手之前先看一眼差异。

- **在插件弹窗里**：勾选收藏夹后点「先看差异」，几秒到一两分钟出结果，弹窗里显示每个收藏夹的摘要。

差异分四类：**新增**（线上有、本地没有）、**线上已移除**（本地有、线上没有了）、**新失效**（本地还是正常、线上已失效）、**已恢复**（本地标记失效、线上正常了）。

**为什么它只要一两分钟，而导入要半小时以上**：差异只读收藏夹列表（一次 40 条），不去逐条抓视频详情（每条限速 1.25 秒）。1000 条约 25 次请求；同样这些条目走一次完整导入要 39 分钟。**这个功能成立的前提就是"不抓详情"**，代码里有测试专门守着这一条。

> 两点说明：① 「线上已移除」指的是你在 B 站取消了收藏，不是本地文件被删了 —— 本地记录一直都在。② B 站收藏夹里的**占位空槽**（视频被删后留下的空位）既不在线上列表里、也不在本地记录里，所以不会被算成差异。

## V1.0.0：第一个正式版

功能与 beta4.9 一致。4.9 交付之后又在真机测试中发现了 6 个问题，全部在这一版修掉：

- **修掉一个会让导入直接失败的缺陷**（最严重的一个）。B 站对「页面上下文」发出的请求本来就返回 HTTP 412，旧版本遇到它会退回后台重试一次、通常能成功；4.9 新加的风控识别只看到错误消息里有 "HTTP 412" 就判定为风控、不再退回，于是每个请求都被当成风控，连续 5 条即中止整轮——**同一账号同一时刻，旧版本导入 128 条全部成功，4.9 却在 4 秒内中止**。现在页面请求失败一律退回后台，风控只以后台自己的响应为准。
- **「失败：N」不再误报**。B 站收藏夹里的视频被删除后会留下占位空槽，它计入收藏夹总数但接口不返回。4.9 把这个口径差异当成了「缺失 N 条」并计入失败，报告里会出现一个没有解释的「失败：25」。现在只有真正没读完才计失败，口径差异改为如实说明。
- **导入中止时不再丢失当轮的日志**。风控是在保存阶段抛出的，而那份日志原本要在循环末尾才写进报告——于是报告里只有一个光秃秃的失败数字。
- **扫描进度不再卡在「正在读取 0/0」**。4.8.3 给这条通知加了关闭按钮之后，容器里多了子元素，而进度函数仍在直接写容器的 `textContent`，把那个文字节点和按钮一起删掉了；之后的最终结果全写进了一个脱离页面的节点。**关闭按钮其实也一起消失了。**
- **「更新视频状态」的确认框补上了失效说明**：发现视频已失效时不会覆盖原有资料，只标记为「已失效」（标题变红、封面变灰）——这是 4.4 就定下的行为，但提示里一直没写。
- **「标记为已下载」不再要求你先下载过东西**。默认下载目录 `000视频下载` 原本只在真正下载时才创建，从没下载过的用户点这个按钮只会看到「还没有下载目录」。现在选择保存位置时会顺手建出它，旧用户点标记时也会按需创建。

界面版本号从 `beta4.9` 改为 `V1.0.0`。

### 4.1beta：补全缺失的标签和简介

这是一次**涉及底层逻辑的改动**（会调用 B 站接口并改写本地 `视频信息.txt`），所以单独出一个 beta 目录，编号 4.1.1。

**为什么会有缺失**：导入流程里只有**失效视频**会去抓标签和简介；正常条目的标签字段恒为空、简介字段常为空，于是归档里写着「未知 / -」。

**改了什么**：

1. **导入时补全**：正常条目现在也会调用 `/x/web-interface/view`（取简介，并顺带补上分区、时长、发布时间、UP 主、封面）和 `/x/tag/archive/tags`（取标签）。只补缺失字段，已有内容绝不覆盖。每次导入最多补 30 条、并发 2、每条间隔 420ms，超出的条目会在报告里提示。
2. **收藏库增量补全**：本地收藏库右上角新增「补全缺失资料（N）」按钮。它会统计当前范围内的缺失条目，让你选择本次处理 10 / 20 / 40 条，逐批推进直到补完。**这是给已经躺在硬盘上的老档案用的** —— 因为导入会按 BV/av 去重，老记录不会再次导入，只能就地补。
3. **写回是外科手术式的**：只替换 `【标签】` 那一行和 `【视频简介】` 区块，其余内容逐字不动。写入前还会做完整性校验（必须仍有 `【基本信息】` 和 `【视频简介】`、长度不得腰斩），不通过就跳过这条。

> **这一节记录的是 4.1beta 当时的做法。**其中的「补全缺失资料」按钮和配套试跑脚本 `test/enrich-trial.cjs` **已在 4.2 移除**——导入/更新现在会直接把资料抓全，不再需要事后补。保留这段只为说明当时的取舍。

**风控建议**：一次 20–40 条、分几次点完，比一次性点几百条安全得多。失败或接口没返回的记录会保持原样，可以之后再补。

### 4.2：导入重构 + 暂停取消 + 网页端展示优化

**插件端**

- **导入的每条视频都抓一次完整资料**：`/x/web-interface/view` 取简介、发布时间、分区、时长、UP 主、互动数据，`/x/tag/archive/tags` 取标签，`/x/relation/stat` 取 UP 主粉丝数（按 UP 缓存，同一个 UP 只请求一次）。以前只有失效视频会抓，正常条目标签恒为空、简介常为空——现在不会再出现「未知 / -」。
- **本地没有同名收藏夹时全量导入；已有同名收藏夹时，补齐缺失的视频，并按新格式刷新数据不完整的旧记录**（缺粉丝数/互动数据，或标签、简介、发布时间还是占位值的）。
- **导入过程中可以暂停、继续、取消**。取消会删除本次新建的视频目录、还原本次更新过的 `视频信息.txt`、清掉本次新建的空收藏夹，**导入前就在本地收藏夹里的内容不会被删除**。弹窗关闭再打开也能看到当前进度并继续操作。
- **`视频信息.txt` 排布调整**：新增 `UP主粉丝数` 与独立的 `【互动数据】` 区块（播放量/弹幕量/点赞数/投硬币枚数/收藏人数/转发人数），统计信息不再挤在简介里。
- **简介会自动清理**：收藏夹接口返回的 `intro` 常常是 B 站分享文案（`…, 视频播放量 71953、弹幕量 82…, 视频作者 XXX, 作者简介 YYY, 相关视频：…`），4.2 把真正的简介与统计信息拆开，简介里不再夹带这些内容。

**网页端**

- 顶部显示**本地收藏夹占用空间**（递归统计整个本地备份文件夹）。
- 详情面板把互动数据做成**独立统计卡片行**，UP 主旁边显示粉丝数；没有数据的旧记录不显示这一块。
- 删除了「补全缺失资料」按钮——导入/更新现在会直接把资料抓全。
- 顶部新增提示：如果需要导入或更新本地文件夹内的视频，请在 B 站收藏夹页面点击插件的「导入或更新」。

**试跑**：`node test/import-trial.cjs "<你的本地备份文件夹>" 3` 会只读地预览 4.2 会抓到什么（标签、发布时间、粉丝数、互动数据、清理后的简介），不改任何文件。

### 4.3：安全与合规加固

**没有新增功能**，只是把审计发现的问题修掉，详见下文「合规与使用边界」。

- 导入请求密度降到**串行 + 每条间隔 800ms**（详见文末「4.3 为降低风险做的改动」）。

这是正式版前最后一个测试版。我们对整个项目做了一次彻底审视（约 8800 行 JS + 本地目录打开助手 + 三个界面），**安全侧未发现致命或高危漏洞**；下面是这一轮真正修掉的东西。

**导入的可靠性**

- **修掉一个会把界面彻底锁死的缺陷**：暂停导入超过约 30 秒，后台会被浏览器回收，而界面仍以为导入在进行——既不能继续也不能取消，只能重装扩展。现在后台会主动保活，并且界面每次读取状态时都会先核对"后台是否真的有导入在跑"，发现是残影就复位并明确告诉你"上次导入已中断"。
- **导入的进度与回滚日志现在能跨进程存活**。浏览器崩溃或后台被回收后重开，你会看到**停在哪个收藏夹第几页、已写入多少条**，而不是一无所知。
- **收藏夹超过 4 万条时不再静默丢数据**。以前会在第 1000 页悄悄停下，报告还显示"失败 0"；现在会把「预期 N 条、实际拉取 M 条、缺失 K 条」明确写进报告和界面提示。
- **识别 B 站风控并立即停止**。以前被限流时，每条视频的资料抓取都会失败，但插件**照样把记录写进去并计入"成功"**——你会拿到一个看似完整、实则标签简介全是「未知」的归档。现在连续触发即中止，并告诉你等多久再试。顺带修掉一个连带问题：限流码以前会被"更新视频状态"误判成"视频已失效"，把还能看的视频标成失效。
- **半截记录会被自动补全**。以前进程被杀会留下"有信息文件、没封面"的目录，而且会被当成完整记录永远跳过。现在改为先写封面、后写信息文件，让信息文件充当完成标记。

**加载性能**

- **封面从 1.6 MB 缩到约 15 KB**（320×180 WebP）。实测一千张封面就要 200 MB 量级；按老规则，一万条视频光封面就要读十几 GB。老档案里的封面**不动、不重下**，读取时两代文件名都认。
- **缓存不再自我失效**。原来超过 4000 条时缓存会被整表清空，等于在最需要它的规模上失效，而且被清掉的封面 URL 再也没人回收（每点一次「刷新」就泄漏一批）。现在改为按最旧淘汰，并用引用计数保证**只在没人用的时候**才释放。
- **删掉了一个 60 秒的定时全量重扫**。一万条视频时它每分钟要打一万两千次文件系统调用——页面开着就在持续读盘。
- **搜索不再卡顿**。筛选下拉框以前每敲一个字符就整个重建（上万条时要新建上千个选项）；现在改为按需重建 + 250ms 防抖，并预先把搜索索引导出。

**其它**

- **「下载目录不存在」不再被当成「下载目录是空的」**。以前你把 `000视频下载` 改名或移走后，所有视频的"已下载"标记会被清空，界面看起来像文件都没了。
- **本地目录打开助手的安装目录加了限位**（必须位于本用户的 `LOCALAPPDATA` 之下）。卸载脚本以前接受任意目录参数并递归删除，传错一个参数就可能删掉别的文件夹。
## 使用边界（这些是设计约束，不是缺陷）

用之前值得知道几件事，能避免误判：

- **「删除本地收藏夹」不会删除 `000视频下载` 里的视频文件**。删除操作只清理归档记录目录（`视频信息.txt` + `封面.webp`；4.9 之前建的记录用的是 `封面.png`，两种都能正常显示）。如果你手工把下载好的视频直接放进了收藏夹记录目录里，它们不会被删——但也会因此**失去索引**，需要你自己到磁盘上整理。
- **「已下载？点击标记」建的目录名末尾带 ` - BV号`，请不要改掉这个后缀**。插件靠它认出"这条已经下载过了"；改了后缀，标记就会消失（文件本身没事）。
- **浏览器崩溃或被强制结束时，导入不会自动回滚**。只有你主动点「取消导入」才会触发回滚。崩溃后可能停在"导入了一半"的状态，重跑一次导入会跳过已存在的记录。
- **「下载根目录的绝对路径」只是给你复制路径用的**，它不参与任何文件读写。填错了不会损坏任何东西，只是复制出来的路径不对。（1.3.0 起界面上已经没有填写入口，这一档只在老用户身上还留着一个旧值；新的空档案拿不到绝对路径，会直接退回相对路径。）
- **导入大收藏夹需要很久**。出于避免触发 B 站风控的考虑，插件把速率压在约 1.2 条/秒：5000 条约 1.1 小时，10000 条约 2.2 小时，50000 条约 11 小时（还没算网络与写盘）。**请让浏览器保持运行，中途不要关掉。**
- **B 站收藏夹显示的数量可能比实际视频多几条**，这是 B 站的行为、不是导入遗漏。收藏夹里的视频被删除后，B 站**会留下占位空槽**——它仍计入收藏夹总数，但页面上是一块空白，接口也不会返回它。实测：一个显示 239 项的收藏夹，从第 2 页起每页末尾共有 9 个空白槽位，实际视频正好 230 条，导入后本地就是 230 条。导入完成时插件会把这个差额直接告诉你。

## 合规与使用边界（请务必阅读）

**这个扩展会代替你自动请求 B 站接口（导入收藏夹、抓取视频资料），因此它触碰了 B 站《用户使用协议》中的条款。** 1.3.0 起它不再请求视频流地址、也不再保存视频本体，但「代替你自动请求接口」这件事本身仍然涉及下面的条款。这一节把话说清楚，请自行判断是否使用。

### 涉及哪些条款

依据《[哔哩哔哩弹幕网用户使用协议](https://www.bilibili.com/blackboard/protocal/international_hans.html)》：

| 条款 | 内容要点 | 本项目涉及的功能 |
|---|---|---|
| **4.3.15** | 未经书面许可，不得以「机器人程式、蜘蛛程式、爬虫程式等**任何自动程序、脚本、软件**」获取平台的服务、内容、数据 | 自动归档、收藏夹导入、批量抓取元数据 |
| **1.2** | 服务「均限于在哔哩哔哩内使用」，以任何方法**将服务与哔哩哔哩分离**的行为不属于约定服务 | **1.3.0 起已移除**：插件不再请求视频流地址，也不再保存视频、音频、弹幕或字幕文件 |
| **1.3** | 官方公布的方式是使用服务的**唯一合法方式**，借由其他途径获取的服务「均为非法」 | 失效视频恢复会伪造成官方 iOS 客户端请求 APP 接口（不想走这条路径可在导入面板里取消勾选「尝试恢复失效视频」） |
| **6.5** | 未经许可不得**私自转载、传播**或提供观看服务 | 若你把归档下来的资料，或自己下载后放进收藏夹的那些视频分享出去 |
| **2.6 / 8.3** | 违反者可被**删除账号、暂停或永久停止服务**，且无需事先通知 | 潜在后果 |

**这不是本项目独有的问题**——所有第三方 B 站下载/归档工具都处在同一位置。协议没有为「个人自用归档」留例外。

### 实际风险有多大

- **最现实的风险是触发风控**（412、临时限制、需要验证码），通常与请求频率和批量规模相关。
- 账号被临时封禁、永久删除属于协议授权范围内的处罚，但**针对个人自用规模极少执行**。
- **真正的法律风险在你自己手里**：把归档下来的封面与 `视频信息.txt`，或你自己下载后放进收藏夹的那些视频**上传、分享、二次发布**，就同时违反协议 6.5 和《著作权法》，性质从「违约」变成「侵权」。

### 请遵守的使用边界

1. **只用于自己的账号、自己有权观看的内容。** 不要用它去抓取他人无权访问的内容。
2. **产出的文件只留给自己。** 不要上传、分享、二次发布，也不要用于任何商业用途。
3. **不要批量轰炸接口。** 导入已经做了限速（串行 + 每条间隔 800ms，约 1.2 次请求/秒），请不要再自行调快；一次选一两个收藏夹，分几次完成。
4. **不要让它长时间无人值守地跑大批量任务。**
5. 参考《著作权法》第二十四条，「为个人学习、研究或者欣赏」使用他人已发表作品属于合理使用——这条边界只覆盖**你自己看**。

### 4.3 为降低风险做的改动

- 导入请求密度下调到**串行 + 每条间隔 800ms**（原为并发 2 + 350ms，约 5.7 次/秒）。
- **失效视频恢复默认开启（4.4.1 起）**：它需要伪造官方 iOS 客户端去请求 APP 接口，属于合规上最勉强的一环。如果你不希望走这条路径，可以在插件弹窗的导入面板里取消勾选「尝试恢复失效视频」。
- 关掉自动归档开关即可完全停止自动行为；不选目录则扩展不会读写任何本地文件。

### 代码层面的安全属性（已核查）

- **从不修改 B 站服务端状态**：全部请求都是 GET，没有 POST/PUT/DELETE，不可能误删你的线上收藏或代替你发言。
- **无第三方域名、无遥测**：出网域名只有 `api.bilibili.com` 与 `*.hdslb.com`（图片 CDN）。**1.3.0 起 `*.bilivideo.com`、`*.bilivideo.cn`、`*.akamaized.net` 这三条视频流域名权限已从 `manifest.json` 中删除** —— 这是「插件已经没有取流能力」在代码层面最直接的证据。
- **无远程代码**：没有 `eval`、没有动态加载脚本、MV3 默认严格 CSP，也没有任何 npm 依赖。
- **扩展页不对任何网页开放**：`library.html` 不作为 web_accessible resource 暴露，并额外拒绝被 iframe 嵌套。
- **错误报告含本地路径**，文件里已加提示，请勿公开分享。
